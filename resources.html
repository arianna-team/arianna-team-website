The platform

What is ARIANNA?

A SaaS platform that enables device manufacturers to implement an efficient & effective vulnerability management process. ARIANNA builds a comprehensive model of each device combining its SBOM, HBOM and security context. It continuously monitor new vulnerabilities, enriches vulnerability data with proprietary intelligence, prioritises relevant risks, guides your triage and remediation activities, and provides the evidence needed to demonstrate compliance with the CRA, RED and your customers requirements.

Where is our data hosted?

In the European Union. With the Enterprise plan you also get a dedicated instance of the platform.

SBOM & HBOM

What is a Device Model?

A model of your device that contains the list of hardware & software components, and the information relevant to its security context. It is organised by Processing Unit: for each one, the hardware (HBOM) and then the operating system and software layers on top of it (SBOM).

Do I need a Device Model for every unit we ship?

No. You create one Device Model per device design, whether you ship one unit or a thousand. Each new firmware release becomes a new version of the same model.

Which software stacks are supported?

Microcontroller firmware (bare-metal and RTOS, including Zephyr and the main silicon vendor SDKs), Embedded Linux (Yocto, Buildroot, OpenWRT, Debian, RedHat and more), Windows, Android, applications in common languages, and cloud and container environments. See the full list of supported environments on the Platform page →

Do we need to provide a ready-made SBOM?

No. ARIANNA provides a wide set of its own SCA tools, one for each software stack, that create the SBOM straight from your build.

Do we have to share source code or binaries?

No. ARIANNA's SCA tools run in your own build environment and only send the component list (vendor, name, version and, where available, licences, patches and dependencies). There is no reverse engineering of binaries.

Do we need to install agents on our devices?

Nothing is installed on your devices. No agents, no additional software to maintain in the field, and no risk of disrupting, interfering with or limiting their normal operation. No false alarms caused by intrusive monitoring. No device-side updates to manage.

Do our devices need to be connected to ARIANNA?

No. The vulnerability assessment report is produced from the Device Model (your HBOM and SBOM), not from the devices themselves. Nothing in the field connects to ARIANNA.

Can we automate SBOM updates in our CI/CD pipeline?

Yes. The SCA tools are lightweight Python, Bash or PowerShell scripts that can be easily integrated as final stage of your CI/CD pipeline. Run them after each release, update an existing Device Model by uploading the SCA Tools output through the REST API provided by ARIANNA, and a new assessment starts automatically.

How is the HBOM created?

You can build a list of relevant hardware components through a guided process in the ARIANNA web interface. Simply select the hardware vendor and part number from ARIANNA's hardware catalogue, and the platform automatically enriches each component with additional technical details, such as internal cores, GPUs and other hardware characteristics.

Vulnerability management

Which vulnerability sources do you monitor, and how often?

ARIANNA maintains an internal vulnerability intelligence database, updated daily with new findings from authoritative sources (including NIST NVD, CVE.org, GitHub Security Advisories and ENISA's European Vulnerability Database (EUVD))and security advisories published by major silicon vendors. Each finding is enriched with proprietary intelligence, including information on known exploitation in the wild, evidence from authoritative exploitation-tracking sources (such as the CISA KEV and ENISA KEV catalogues) and internet-deployed honeypots, exploit availability and maturity levels, and EPSS scores. This additional context enables more accurate vulnerability prioritisation and better-informed remediation decisions.

How do you keep false positives down?

Accurate SBOMs from the build are the first step. ARIANNA then discards findings automatically when the affected version is no longer present, the component was updated or patched, the functionality is not in use, or the source re-evaluated the vulnerability.

How are vulnerabilities prioritised?

The ARIANNA pre-triage engine automatically marks each open vulnerability High or Low priority using rules you configure, by risk, by exploitability (KEV, exploits, EPSS, attack vector exposure) or both. 

What happens when we release a new firmware version?

You create a new version of the Device Model. Your triage work carries over, vulnerabilities in updated, patched or removed components close automatically, and new components are checked straight away.

Can we manage vulnerabilities found in our own pentests?

Yes. Add vulnerabilities from penetration tests, code reviews or responsible disclosure by hand, and manage them in the same workflow as everything else.

Compliance

How does ARIANNA help with the Cyber Resilience Act?

It covers the vulnerability-handling side of the CRA: an SBOM for every version, monitoring for the whole support period, prioritised remediation with deadlines, and an auditable record of every decision, exportable as CycloneDX, SPDX, VEX or PDF. Learn more about the CRA and ARIANNA →

Does ARIANNA help with the 24-hour reporting obligation?

ARIANNA flags vulnerabilities that others, such as other manufacturers reporting to ENISA, have found to be actively exploited, so you can check and prioritise them in your own products straight away. Detecting that your own product is being exploited needs your own sources, such as customer reports, incident response or field monitoring. 

Is ARIANNA relevant for the RED Delegated Act?

Yes. It provides the vulnerability assessment and risk-management evidence for radio equipment, and the same process carries over to the CRA.
